# PostgreSQL 与 MySQL 在高并发写入场景下的取舍

## 引言
在现代应用中，数据库的性能、扩展性和功能直接影响项目的成败。PostgreSQL 和 MySQL 作为目前最受欢迎的两大开源关系型数据库，各自拥有独特的优势。本文将重点讨论在高并发写入场景下，PostgreSQL 与 MySQL 的性能表现和适用性，并基于最新的测试数据和案例分析，提供具体的选型建议。

## 高并发写入场景下的性能对比

### 纯写入极限场景
在纯写入极限场景下，PostgreSQL 和 MySQL 的性能几乎持平。根据 [1] 中的测试结果，在相同的硬件配置和优化参数下，PostgreSQL 的 TPS（每秒事务数）为 9,500，而 MySQL 的 TPS 为 8,000。这表明在纯写入操作中，PostgreSQL 略微领先，但差距不大。

### 并发写入延迟
在高并发（≥1000 连接）的情况下，PostgreSQL 的平均延迟约为 MySQL 的一半。具体来说，[1] 中提到，在 1000 并发连接下，MySQL 的延迟为 80 毫秒，而 PostgreSQL 的延迟仅为 40 毫秒。这一显著差异主要归因于 PostgreSQL 的 MVCC（多版本并发控制）机制，该机制在高并发读写环境下表现出色，有效降低了锁冲突。

## 并发模型与扩展性

### 并发模型
- **MySQL**：采用线程池+行锁的并发模型。在高并发情况下，线程池模型容易出现上下文切换瓶颈，导致性能下降。
- **PostgreSQL**：采用 MVCC+快照的并发模型。MVCC 机制通过创建数据的多个版本来实现无锁读，从而在高并发写入场景下表现出更好的稳定性和更低的延迟。

### 最大连接数
- **MySQL**：最大连接数约为 4,000，受限于线程开销。
- **PostgreSQL**：最大连接数可达 10,000，得益于其进程+轻量锁的并发模型，更适合高并发环境。

### 并行查询
- **MySQL**：并行查询能力有限，仅支持 InnoDB 存储引擎的部分并行操作。
- **PostgreSQL**：具备全功能并行查询能力，包括 gather 和 worker 机制，能够更好地处理复杂查询和高并发写入。

## 实战选型建议

### 业务特征与推荐
- **读多写少、简单 SQL、需要分库分表**：推荐使用 MySQL。MySQL 在高频简单读写和读多写少的 Web/电商类业务中综合性能更快，适合快速上线和简单的应用场景。
- **写密集、高并发、事务延迟敏感**：推荐使用 PostgreSQL。PostgreSQL 在高并发写入场景下表现出色，特别是在复杂的 JOIN、窗口函数、CTE 和分析型查询中，性能优势明显。
- **复杂报表、窗口函数、CTE、JSONB**：推荐使用 PostgreSQL。PostgreSQL 的查询优化器、并行执行和丰富索引（如 GIN、GiST、BRIN）对复杂 SQL 提升显著。
- **云原生 SaaS（连接数多）**：推荐使用 PostgreSQL。PostgreSQL 支持更多的并发连接数和全功能并行查询，更适合云原生 SaaS 应用。
- **团队熟悉 LAMP、快速上线**：推荐使用 MySQL。MySQL 的配置相对简单
