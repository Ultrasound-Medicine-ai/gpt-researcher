# Redis 分布式锁的实现原理与常见坑

## 实现原理

在分布式系统中，确保资源的互斥访问是一个关键问题。Redis 作为一种高性能的键值存储系统，在实现分布式锁方面被广泛应用。Redis 分布式锁的核心在于利用其原子操作来保证互斥性。

### 基础实现

1. **SETNX 命令**：`SETNX`（Set if Not Exists）命令用于在指定 key 不存在时设置值，否则不执行任何操作。该命令是原子性的，可以保证并发场景下的互斥性。
2. **加锁逻辑**：通过 `SET` 命令结合 `NX` 和 `EX` 参数，可以在设置 key 的同时设置过期时间，确保加锁和设置过期时间的操作是原子的。例如：
   ```java
   Boolean result = redisTemplate.opsForValue().setIfAbsent(key, value, expireMs, TimeUnit.MILLISECONDS);
   ```
3. **释放锁逻辑**：为了防止误删其他客户端持有的锁，需要使用 Lua 脚本来保证删除操作的原子性。Lua 脚本会先检查 key 对应的 value 是否为当前客户端的唯一标识，确认后再删除 key。
   ```lua
   if redis.call('get', KEYS[1]) == ARGV[1] then return redis.call('del', KEYS[1]) else return 0 end
   ```

### 进阶优化

1. **锁续约机制**：为了避免业务处理时间超过锁的过期时间导致锁提前释放，可以引入锁续约机制。通过启动一个后台线程定期延长锁的过期时间，直到业务处理完成再主动释放锁。Redisson 框架内置了这种机制，称为“看门狗”。
2. **高可用方案**：单点部署的 Redis 存在单点故障风险。可以通过主从复制 + 哨兵模式或 Redlock 算法来提高系统的高可用性。Redlock 算法通过向多个独立的 Redis 主节点发起加锁请求，只有当超过半数节点加锁成功才算整体加锁成功，从而避免单点故障。

## 常见坑点

### 死锁问题

1. **未设置过期时间**：如果程序在执行业务过程中突然宕机，没有执行删除锁的逻辑，会导致死锁。解决方法是在加锁时设置过期时间，并确保设置 key 和过期时间的操作是原子的。
2. **误删他人持有的锁**：在释放锁时，直接删除 key 可能会误删其他客户端持有的锁。解决方法是通过唯一标识符验证锁的所有权，只有持有锁的客户端才能释放锁。

### 锁提前释放

1. **业务处理时间过长**：如果业务处理时间超过锁的过期时间，锁会自动释放，导致其他客户端可以获取锁，进而引发并发冲突。解决方法是引入锁续约机制，定期延长锁的过期时间。

### 单点故障

1. **单点部署风险**：单点部署的 Redis 在服务宕机时会导致所有分布式锁操作失效。解决方法是采用 Redis 集群部署，如主从复制 + 哨兵模式或 Redlock 算法，提高系统的高可用性。
