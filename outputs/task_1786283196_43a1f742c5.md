# Redis 分布式锁的实现原理与常见坑

## 引言
在分布式系统中，确保共享资源的互斥访问是一个关键问题。Redis 作为一种高性能的键值存储系统，在实现分布式锁方面被广泛应用。本文将详细介绍 Redis 分布式锁的实现原理，并探讨常见的陷阱和解决方案。

## Redis 分布式锁的实现原理

### 基本概念
分布式锁的核心需求是互斥性，即同一时间只有一个服务实例能持有锁。此外，还需要满足高可用、防死锁、可重入等特性。Redis 实现分布式锁主要依赖于其原子操作，通过键值对的存删来标记锁的占用与释放[1]。

### 基础实现
#### SETNX 命令
Redis 的 `SETNX` 命令（SET if Not Exists）是实现分布式锁的基础。该命令在指定 key 不存在时设置值，否则不执行操作。早期版本中，加锁需分两步执行（`SETNX` + `EXPIRE`），但这两步并非原子操作，存在并发漏洞。从 Redis 2.6.12 版本开始，支持 `SET` 命令多参数合并，可以一次性完成加锁、设值、设过期时间，保证原子性[2]。

```bash
SET lock:stock:1001 random-value NX PX 30000
```

### 进阶优化
#### 锁续约机制
为避免锁过期提前释放，引入“锁续约”机制。服务成功加锁后，启动一个后台线程，每隔一定时间检查锁是否仍被当前服务持有，若持有则延长锁的过期时间，直到业务逻辑执行完成再主动释放锁。Redisson 框架内置了 Watch Dog 机制，自动完成续约操作[3]。

#### 高可用方案
单点故障风险可以通过基于 Redis 集群的高可用方案解决。常见的方案包括主从复制 + 哨兵模式和 Redlock 算法。Redlock 算法向至少 3 个独立的 Redis 主节点发起加锁请求，仅当超过半数节点加锁成功且总耗时不超过超时时间，才算加锁成功[4]。

## 常见坑及解决方案

### 误删他人持有锁
**成因**：释放锁时未做身份校验，直接执行 `DEL` 命令删除键。
**表现**：多个服务实例同时持有同一把锁，操作同一资源，出现数据不一致。
**解决方案**：加锁时存入全局唯一的随机值作为 value，释放锁前先验证 value 是否与自身持有一致，一致才释放。使用 Lua 脚本保证“验证+删除”的原子性[5]。

### 锁过期提前释放
**成因**：锁的过期时间设置过短，而业务逻辑执行耗时过长，导致锁在业务完成前就自动过期释放。
**表现**：业务执行中锁被释放，多个服务同时操作资源，出现数据错误。
**解决方案**：引入“锁续约（Watch Dog）”机制。服务成功加锁后，启动后台守护线程，每隔锁过期时间的 1/3 检查锁是否仍被自身持有，若持有则延长锁的过期时间[6]。
