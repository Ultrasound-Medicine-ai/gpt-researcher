# RAG 场景下向量数据库选型对比：Milvus vs pgvector vs Qdrant

在检索增强生成（RAG）系统中，向量数据库承担着“记忆引擎”的关键角色，其选型直接影响系统的检索质量、延迟与扩展性 [7]。以下从架构、性能及适用场景三个维度，对 Milvus、pgvector 和 Qdrant 进行深度对比。

## 架构与扩展性对比

**Milvus** 采用云原生分布式架构，支持存算分离，组件包括 Proxy、Coordinator、DataNode 等，天生具备水平扩展能力，可部署于 Kubernetes 环境 [5][7]。其设计目标是应对超大规模数据，支持动态分片与多副本，是大规模企业级应用的事实标准 [7]。

**Qdrant** 基于 Rust 语言开发，兼顾性能与安全性。它支持内存与磁盘混合存储，并提供云服务与自托管两种模式 [7]。其架构支持分片与副本，具备良好的分布式扩展潜力，且部署相对 Milvus 更为轻量 [5][7]。

**pgvector** 本质上是 PostgreSQL 的扩展插件，并非独立的向量数据库。它复用了 PostgreSQL 的成熟生态，支持 SQL 查询与向量检索的混合，但在架构上受限于关系型数据库，难以像专用向量数据库那样进行灵活的水平扩展 [6][9]。

## 性能与功能特性

在性能表现上，**Qdrant** 凭借 Rust 的高效实现，在过滤查询和低延迟场景下表现优异，P99 延迟可低于 20ms，资源利用率高 [1][10]。**Milvus** 在大规模数据下吞吐量表现稳定，P99 延迟约为 50ms，支持 GPU 加速，适合高并发场景 [1]。相比之下，**pgvector** 的性能受限于 PostgreSQL 的架构，P99 延迟通常在 100ms 以上，索引构建速度较慢，更适合对延迟不敏感的场景 [1][5]。

在功能层面，三款工具均支持混合搜索（向量+关键词），但实现方式不同。**Milvus** 支持稀疏向量与标量数据的混合检索，功能最为全面 [5]。**Qdrant** 原生支持 BM25 全文检索与复杂的 Payload 过滤，过滤能力强大 [1][5]。**pgvector** 则通过 `tsvector` 与向量的联合查询实现混合搜索，优势在于能直接利用 SQL 进行复杂的关系型数据处理 [1]。
