# 项目一验收短报告：Redis 分布式锁原理

## 核心机制与原子性保障
### 加锁与解锁逻辑
Redis 分布式锁的实现基础在于其单线程执行模型与原子命令。加锁操作严格依赖 `SET key value NX PX timeout` 指令，其中 `NX` 保证资源互斥访问，`PX` 设定自动过期时间以防范客户端异常宕机导致的死锁[2]。解锁环节严禁直接使用 `DEL`，必须通过 Lua 脚本校验客户端唯一标识（Token）后再执行删除，确保“校验-删除”操作的原子性，彻底杜绝误删其他客户端锁的风险[3]。

## 锁续期与集群容错
### 续期机制与多节点共识
固定 TTL 存在业务执行超时导致锁提前释放的隐患。生产环境普遍采用 Redisson 客户端，其内置的 WatchDog（看门狗）机制会在业务线程存活期间，以默认 30 秒为周期自动续期，保障长耗时任务的互斥安全[7]。针对集群架构，单节点主从异步复制可能引发锁丢失。为此引入 Redlock 算法，要求客户端在 N 个独立 Master 节点上并发加锁，仅当成功获取多数派（N/2+1）节点锁且总耗时小于有效期时，方判定加锁成功[8]。

## 核心特性对比
| 特性维度 | 基础实现 | Redisson 增强 | Redlock 集群 |
|---|---|---|---|
| 互斥保障 | SET NX | Lua 原子校验 | 多数派共识 |
| 过期策略 | 固定 TTL | WatchDog 自动续期 | 动态计算有效窗口 |
| 容错能力 | 单点故障即失效 | 依赖主从/哨兵 | 容忍 (N-1)/2 节点宕机 |

## 验收结论
本项目方案已完整覆盖分布式锁的互斥性、防死锁、原子释放及自动续期等核心指标。结合 Redisson 客户端与合理的超时策略，该机制可高效支撑常规高并发场景下的资源竞争控制。在极端网络分区或主从切换场景下，建议配合业务幂等性设计进行最终一致性兜底，以确保系统整体数据可靠性[12]。
