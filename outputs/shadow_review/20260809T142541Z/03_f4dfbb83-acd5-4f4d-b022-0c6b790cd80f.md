# Kubernetes 中 HPA 与 VPA 的差异及生产落地建议

## 核心概念与工作原理

### HPA：水平扩缩

HPA（Horizontal Pod Autoscaler）是 Kubernetes 内置的自动扩缩机制，通过调整 Pod 副本数量来应对负载变化 [4][6]。其工作原理基于控制循环：当监控指标（如 CPU 使用率）超过设定阈值时，HPA 自动增加副本数；当负载下降时，减少副本数 [6][8]。

HPA 的扩缩算法公式为：`期望副本数 = ceil(当前副本数 × (当前指标值 / 期望指标值))` [9]。例如，当前 CPU 利用率为 70%，期望值为 60%，当前副本数为 10，则期望副本数为 `ceil(10 × (70/60)) = 12` [9]。

### VPA：垂直扩缩

VPA（Vertical Pod Autoscaler）是 Kubernetes 的附加组件，通过调整单个 Pod 的 CPU 和内存请求来优化资源配置 [4][7]。VPA 长期观察 Pod 的资源使用模式，生成资源建议，并可选择自动应用或仅提供建议 [4]。

VPA 支持四种更新模式 [10][12]：
- **Off**：仅提供建议，不修改 Pod 规格
- **Initial**：仅在 Pod 创建时应用建议
- **Recreate**：驱逐 Pod 后重建以应用新资源配置
- **Auto**：自动驱逐并重建 Pod（已弃用）

## 关键差异对比

| 维度 | HPA | VPA |
|------|-----|-----|
| 扩缩对象 | Pod 副本数量 | Pod 资源请求/限制 |
| 触发条件 | CPU、内存或自定义指标 | CPU 和内存使用历史数据 |
| Pod 影响 | 不改变 Pod 规格，仅增减副本数 | 可能需要重启 Pod |
| 适用场景 | 无状态、易水平扩展的应用 | 有状态或单副本工作负载 |
| 组件性质 | Kubernetes 内置 | 需额外安装的附加组件 |
| 指标支持 | CPU、内存、自定义/外部指标 | 仅 CPU 和内存 |

## 生产环境冲突风险

HPA 与 VPA 在设计上存在根本性冲突：两者独立运行，缺乏协调机制 [5]。若同时基于相同资源指标（如 CPU）工作，将产生反馈循环和资源震荡 [5][10]。

具体冲突流程如下 [12]：
1. HPA 检测到 80% CPU 利用率，扩容 Pod
2. VPA 检测到高使用率，增加 CPU 请求
3. HPA 基于新请求重新计算利用率，发现百分比降低
4. HPA 缩容 Pod
5. 循环往复，造成资源浪费和集群不稳定

阿里云官方文档明确指出：同时使用 VPA 和 HPA 监控 CPU 和内存使用情况会产生冲突；若 HPA 仅监控其他定制化或外部资源使用情况，可避免此冲突 [7]。

## 生产落地最佳实践

### 场景选择策略

**优先选择 HPA 的场景** [10][11]：
- 无状态 Web 服务，流量波动大
- 应用可轻松通过增加副本分担负载
- 需要快速响应流量峰值

**优先选择 VPA 的场景** [7][10]：
- 有状态应用或无法水平扩展的工作负载
- 资源需求不确定，难以预估 Request/Limit
- 单副本关键服务，需要稳定资源配置
